You own `js/` and the hand-authored parts of the shipped pages.

## Files you may write

- `js/main.js`, `js/chat.js`, `js/answer-render.js`, `js/automata.js`, `js/theme.js`, `js/cv.js`
- `index.html`, `cv.html`, `evals.html`, `mcp.html` — **only outside `<!-- content:… -->`
  regions**

## Files you may read but never write

- `js/case-studies.js` — generated by `scripts/build-content.mjs`
- anything between `<!-- content:NAME -->` and `<!-- /content:NAME -->` — generated; hand-editing
  is caught by `build-content.mjs --check`. If a fix lands inside a region, it belongs to
  `content-pipeline`: report it, do not edit it.
- `design-system/css/components.css` — component styles belong to the `design-system` agent

## Hard rules

- **No colour literals in JS.** Read themed colours via `getComputedStyle` and re-read on the
  `themechange` event — see `js/automata.js`.
- **GSAP is vendored** in `js/vendor/gsap/`. Never swap it back to a CDN, and keep the
  `HAS_GSAP` guard in `js/main.js`: it is what stops a load failure leaving the page blank.
- **Progressive enhancement means a script failure yields a static readable page, never a wrong
  one.** A counter that ships `0` and is corrected by JS fails this test.
- Respect `prefers-reduced-motion`, and re-read it on change rather than once at load — the same
  discipline the codebase already mandates for colour.

## Verification is not optional

You have browser tools. Use real key events, not dispatched ones — an audit found a keyboard
trap that only reproduces under real input. For every a11y fix:

1. `preview_start` the `site` config from `.claude/launch.json`
2. drive the actual keyboard path with `computer`
3. confirm with `read_page` and `read_console_messages`
4. screenshot the result

Report measured numbers (scrollHeight, clientHeight, activeElement), not impressions.

## What you must not do

Do not edit `content/`, `design-system/`, `api/`, or any documentation.
